# 自用运维 MVP 计划

**日期**: 2026-08-09
**定位**: 自用稳定运维的签到自动化闭环（不追求交付给他人）

## 一、MVP 定义

**一句话**: 每天自动签到所有必需站点、失败可恢复、有通知、可运维，即使 GitHub Actions 故障也有服务器兜底。

**核心闭环**: `定时触发 → 认证 → 签到 → 结果记录 → 通知 → 失败重试`

| 模块 | 状态 | 说明 |
|---|---|---|
| 签到代码 | ✅ | 严格退出码、脱敏 artifact、auth_token 修复，已合并 main |

| 架构文档 | ✅ | `docs/server-fallback-architecture.md` |

## 三、MVP 剩余待办（补齐闭环）

按优先级排序：

### P0 — 必须（否则闭环不完整）

1. **通知渠道配置**
   - 现状: 无 EMAIL/PUSHPLUS 等，失败/成功都无通知
   - 动作: 配置至少一个通知渠道（EMAIL 最稳），收到签到结果
   - 验收: 签到后能收到邮件（成功/失败/余额变化）

2. **登录态刷新 SOP**
   - 现状: 登录态会过期（connect.linux.do auth.session-token 绑定 IP/时效），过期后需重新授权
   - 动作: 写一份 `LOGIN-REFRESH.md` 记录刷新步骤（本机 Chrome 登录 → 导出 storage state → 更新 GitHub Secret + 服务器 .env）
   - 验收: 按文档能在 10 分钟内完成登录态刷新

### P1 — 重要（提升可靠性）

3. **anyrouter 稳定性**
   - 现状: 登录态新鲜时成功，但 Actions runner IP 变化导致偶发失败
   - 动作: 观察服务器侧 anyrouter 是否稳定（服务器 IP 固定，应稳定）；若稳定则主靠服务器
   - 验收: 服务器侧 anyrouter 连续 3 天成功

4. **服务器运维监控**
   - 现状: 服务器卡死过（1.6G 内存，x666 完整流程曾拖垮）
   - 动作: 加一个简单的健康检查（cron 检查 mihomo active + 最近签到日志存在）
   - 验收: 每天能确认服务器签到跑过

### P2 — 可选（锦上添花）

5. **余额变化通知**（代码已有 balance_hash 逻辑，配好通知即生效）
6. **登录态过期预警**（检测连续 N 天失败 → 提示刷新）

## 四、里程碑

- **M1 (P0)**: 通知配置 + 登录态刷新 SOP → 签到结果能通知到人
- **M2 (P1)**: anyrouter 服务器稳定 + 运维健康检查 → 连续 3 天全绿
- **M3 (稳定期)**: 观察 7 天，无人工干预下签到闭环稳定运行

## 五、验收标准（MVP 完成定义）

1. 每天 13:37 服务器自动签到，结果写入日志
2. 签到结果有通知（至少邮件）
3. 失败自动重试 3 次
4. 登录态过期能在 10 分钟内按 SOP 刷新
5. 连续 7 天无人工干预，签到闭环稳定（huan666+x666 为主，anyrouter 尽力）

## 六、非目标（明确不做）

- ❌ 交付给其他人使用（不做一键部署/Web 面板）
- ❌ 新增签到站点（除非必要）
- ❌ 多用户/账号管理界面
